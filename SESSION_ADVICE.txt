0. BIGGEST FINDING OF THE WHOLE SESSION — A PRE-EXISTING DATA-LOSS BUG
--------------------------------------------------------------------------
While live-testing the new integrity-resolve mechanism (see section 9),
found and fixed a real, previously-unknown bug: extract_and_save_assumptions
and summarize_async (now summarize_chunk) ran on fire-and-forget daemon
threads. step() returned — and the caller's serialize_engine() ran — almost
immediately after starting them, before their LLM call (1-5s+) had any
chance to finish. Their mutations landed on Entity/Memory objects that were
already orphaned by the time they completed.

Consequence: saved_assumptions, physical_state, and (newly) integrity_resolve
essentially never persisted across turns, for as long as this pattern has
existed — not something introduced this session. Worse: summarize_chunk's
summary is supposed to preserve the content of a history chunk that gets
TRUNCATED immediately after the thread is started. If the summary is lost to
this race (which it almost always was), that chunk of conversation is gone
with no recovery path — real, silent data loss on any session long enough
to trigger compression (MAX_RAW_TURNS).

Fixed by making both run synchronously, positioned so their mutations
complete before serialize_engine() runs (backend/engine/engine.py,
backend/ai_service.py, backend/engine/inference.py). Verified live: resolve
now erodes cumulatively across turns (1.0 -> 0.90 -> 0.80 -> 0.65 -> 0.50 ->
0.35) instead of resetting to 0.90 every single turn as it did before the
fix. This likely also fixes saved_assumptions/physical_state, though that
wasn't separately live-verified — worth a dedicated check.
Tradeoff: turns are now marginally slower (one more synchronous LLM call in
the chain) in exchange for a feature that actually works instead of
silently no-op-ing. Given turns already take 30-100s (section 2 below),
this was the right call, but flagging the tradeoff explicitly.

2. THE BIGGEST FINDING FROM TODAY'S LOAD TEST: TURN LATENCY, NOT CONCURRENCY
------------------------------------------------------------------------------
Ran a 5-client sequential Tier-B baseline (loadtest/) against a live stack.
Zero concurrency — one client at a time. Result: every single turn took
30-70+ seconds. Root cause, confirmed from backend logs, is two compounding
things:
  a) Groq's SDK auto-retries with escalating backoff (8-14s waits, sometimes
     stacked twice) when it hits a rate limit on this API key/tier.
  b) A single turn can trigger up to ~5 sequential Groq calls (main response,
     continuity validator, repair, re-validator, fallback) when the guard
     fires. Each of those calls independently eats its own backoff if
     rate-limited, so the delays compound within one turn.
  c) The specific test scenario's inferred "never_does" rule was unusually
     strict ("would never surrender her power over the archive") and tripped
     the continuity guard on nearly every turn, which is what pushed most
     turns into the full repair chain instead of the fast single-validator
     path (which took 1-3s when it didn't fire).

This is real, reproducible, not a Docker artifact (separate from the DNS
blip noted below) and not something I introduced this session — but it's a
serious production concern nobody had real numbers for before. 30-70s per
turn, from ONE user, on a currently-idle Groq key, is well past what the
fake-streaming UX (buffer-then-reveal) can gracefully hide, and Groq's
rate limits are per-API-key — concurrent real users would share and
compound this, not avoid it.
-> Before shipping to real users: check what Groq tier/plan this key is on
   and what its actual RPM/TPM limits are. If it's the free tier, this alone
   may be the dominant latency problem long before any backend capacity
   limit is reached.
-> Separately worth investigating: why did this scenario's guard fire on
   almost every turn? If that's typical (not a fluke of this one generated
   character), the repair chain firing routinely — not just on edge cases —
   is itself a latency and cost driver worth understanding.

9. THE INTEGRITY-RESOLVE GUARD MECHANISM, AND EVERYTHING FOUND CHECKING IT
--------------------------------------------------------------------------
Built per your direction: NPCs' "would never..." rule now erodes gradually
based on in-scene emotional impact ("a rope loosened by behaviour"), not
player argument. Entity gained integrity_resolve (1.0 -> 0.0, one-directional)
and integrity_notes. Four bands — INTACT/TESTED/WORN/BROKEN — read by both
build_system (generation) and guard_response (validation) so the writer and
the validator agree on how much give a boundary currently has. A boundary
crossed abruptly with no in-scene resistance is always a violation regardless
of resolve, closing the obvious loophole.

Live-tested against a "grieving archivist" scenario, 5 scripted turns
escalating from quiet presence to a direct question about her dead sister.
Confirmed working end to end after the section-0 fix: resolve eroded
1.0->0.90->0.80->0.65->0.50->0.35, and the narration's tone visibly tracked
it — turn 5 showed real internal conflict (clenched fist, flash of fear)
instead of a flat, repeated refusal.

Found and fixed along the way, all verified by tests and/or the live run:
  - Race condition — see section 0, the big one.
  - Guard duplicate-response detection only caught EXACT repeats
    (_same_raw_response). In production, the repair step reused an entire
    previous paragraph verbatim with one sentence appended — real, visible
    to a player, and undetected. Added _similar_response (difflib-based
    fuzzy match) and wired it into both the repair path (previously had ZERO
    anti-repetition check at all) and the existing fallback path. Threshold
    (0.75) is a guessed starting point, not empirically tuned — same caveat
    as the resolve mechanism's band cutoffs and delta ranges below.
  - worker.py never called logging.basicConfig() — main.py does, worker.py
    didn't, so every INFO-level log from prefab/init jobs (including this
    session's own NPC-classification-fallback logs) was likely being
    silently dropped in production. Fixed; verified live, worker logs are
    now properly formatted.
  - arq_pool.enqueue_job() calls in publish_scenario/create_session/
    retry_prefab were unguarded — if Redis was briefly unreachable exactly
    at enqueue time, the request 500'd AFTER already committing
    is_published=True/prefab_status=pending (or a session placeholder),
    leaving a stuck resource with no automatic recovery. Now caught, and
    prefab_status/session status flip to failed/error consistently with
    how an in-flight job failure is already handled.
  - worker had no dependency on backend being ready, only on postgres/redis
    — implicitly relied on "nothing enqueues a job before the API is up."
    Added a real backend healthcheck (docker-compose.yml) and made worker
    depend on it — verified live, worker now visibly waits for backend to
    report healthy before starting.
  - PREFAB_JOB_KEY's Redis counter (concurrency gate on prefab jobs
    specifically, separate from arq's own global max_jobs) could leak
    permanently if the worker crashed between incr and the decr in finally.
    Gave it a rolling TTL so a leak self-heals within minutes instead of
    degrading prefab throughput forever.
  - end_session didn't coordinate with the per-session turn lock at all — a
    concurrent end_session could interleave SessionLog writes with an
    in-flight turn. Added a bounded best-effort wait (up to 3s) for the
    lock to clear before checkpointing; proceeds anyway after that with a
    warning logged, since turns can legitimately take 30-100s+ and
    end_session must not hang that long.
  - resolve_shift (and the pre-existing saved_assumptions/physical_state
    extraction) matched character names by exact string equality — a
    nickname or rephrasing would silently no-op with no signal. Normalized
    to case/whitespace-insensitive matching across all three, and added a
    warning log when a name matches no entity at all (distinct from
    matching an entity that simply has no tracked boundary, which is
    expected and stays silent).

Still true, not addressed: the band cutoffs (71/41/11%) and per-turn delta

11. THE REAL RAMP TEST — PRECISE ROOT CAUSE FOUND: TPM, NOT TPD
--------------------------------------------------------------------------
Ran the actual concurrency ramp (3->12 clients) live against Groq, per your
direction to let backoff happen naturally and only stop on a genuine
sustained failure. First attempt was invalid: the harness's own thresholds
(from a 2-client baseline) were so tight that a normal latency blip on a
CHEAP step (e.g. create_persona at 249ms vs. an 80ms threshold) aborted the
whole client before it ever reached a turn call — tiers "completed" in 4
seconds, which was the tell. Fixed: latency_breach is now recorded, not
fail-fast (backend/loadtest/scenarai_client.py, run.py) — only a genuine
hard_error or silent_bad_state stops a client's scripted flow now, matching
the "slow is not broken" principle you gave.

Reran with the fix. Real result: 100% hard_error at concurrency=3, the
lowest tier tested. Root cause, read directly from backend logs:

  groq.RateLimitError: Error code: 429 - Rate limit reached for model
  `llama-3.1-8b-instant` ... on tokens per minute (TPM): Limit 6000,
  Used 5460, Requested 2391. Please try again in 18.5s.

This is TPM (tokens/minute), not TPD (tokens/day) — worth correcting since
it changes the read. engine/call.py's backoff is already correct and
graceful: it parses Groq's own "try again in Xs" and waits exactly that
long (not a blind exponential guess), for up to 6 attempts. The failure
mode isn't bad backoff — it's a thundering herd: with 3-12 clients all
rate-limited simultaneously, they all get told to wait roughly the same
~15-25s, all retry at roughly the same moment, collide on the same
just-refreshed 6000-token budget again, and repeat. 6 attempts is not
enough to break that cycle under real concurrency, so call() eventually
raises RuntimeError, which is what surfaces as hard_error on turns and
silent_bad_state (session_init_error / prefab_missing) on init/prefab.

The practical conclusion: 6000 TPM is small enough that a single full
guard-chain turn (up to ~5 chained calls) already uses a meaningful
fraction of it. At 3 truly concurrent players, the account is saturated
before backend infrastructure (Postgres/Redis/arq/FastAPI) is anywhere
near being tested. This specific Groq key cannot be used to find
Scenarai's actual backend capacity ceiling — the number the ramp would
report is Groq's account-level TPM ceiling, not Scenarai's. Groq's own
error message points at the fix: "Upgrade to Dev Tier." A higher-tier key
is the only way to raise this specific number; no client-side patience or
retry-budget tuning changes it, since the constraint is the account's fixed
per-minute pool, not this app's code.

Temporary rate-limit bump (register/create_session raised to 1000/min for
this test only, to remove a confound from slowapi's own per-IP limiting)
has been reverted. 232/232 tests still pass.
